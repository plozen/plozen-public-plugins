# Background Dispatch Skill

이 스킬은 background subagent를 띄운 뒤 메인 에이전트가 사용자와 계속 대화할 수 있게 하는 운영 규칙이다. 구현/조사 자체를 대신하는 스킬이 아니라, `spawn_agent` 이후의 대화 양보와 lifecycle 관리를 강제한다.

## 사용 시점

다음 경우에만 사용한다.

- 현재 작업을 시작한 사용자 입력의 마지막 토큰이 `-bd`다.
- 기존 `-bd` 작업에서 이미 스폰한 subagent의 lifecycle이나 결과를 후속 turn에서 관리한다.

`-bd` 없이 "백그라운드", "병렬", "서브에이전트"라는 표현만 있는 경우에는 새 subagent를 호출하지 않고 `-bd`를 붙여야 한다는 규칙을 안내한다.

## Authorization gate

- 입력 양끝 공백을 제거한 뒤 마지막 독립 토큰이 정확히 `-bd`인지 확인한다.
- `-bd`는 subagent 사용 허가이지 강제 호출 명령이 아니다.
- 허가 후에도 작업의 독립성, 지연 이점, 충돌 위험을 보고 현재 에이전트가 직접 수행할지 subagent를 사용할지 자율 판단한다.
- `-bd`가 없으면 복잡성, 작업량, 역할 분리, 장시간 실행을 근거로 새 subagent를 호출하지 않는다.
- 이미 승인된 `-bd` 작업의 기존 agent를 관리하는 후속 turn에는 `-bd` 반복 입력을 요구하지 않는다.

## 핵심 규칙

1. 같은 역할과 같은 작업 라인의 subagent는 재사용을 기본값으로 한다. 새 `spawn_agent` 전 기존 agent에 `send_input`으로 이어갈 수 있는지 먼저 확인한다.
2. `completed` 상태는 "결과가 도착했다"는 뜻이지 자동 종료 신호가 아니다. 후속 피드백 가능성이 있으면 세션을 유지하고 `send_input`으로 이어간다.
3. 실수로 닫았지만 같은 작업 라인을 이어갈 가치가 있으면 새로 만들기 전에 `resume_agent`를 먼저 시도한다.
4. 새 `spawn_agent` 호출은 기존 agent 재사용이 부적합하거나 역할/파일 ownership이 달라 충돌 위험이 있을 때만 한다. 스폰된 작업은 백그라운드로 취급한다.
5. 스폰 직후 `wait_agent`를 기본 호출하지 않는다. 결과가 즉시 critical path를 막을 때만 기다린다.
6. 스폰 직후 긴 웹검색, 중복 조사, 대량 파일 읽기 같은 foreground 작업을 이어가지 않는다. 먼저 짧게 디스패치 사실을 보고하고 사용자 입력을 받을 수 있게 한다.
7. 사용자가 중간에 다른 질문을 해도, 새 요청이 기존 background 작업과 충돌하지 않으면 subagent를 닫지 않는다.
8. 사용자가 `Esc`, turn abort, 새 질문, 상태 질문을 보냈다는 이유만으로 취소 의도로 해석하지 않는다.
9. `close_agent`는 사용자가 명시적으로 "중단", "취소", "닫아", "그 작업 버려", "이 작업 라인 끝"이라고 했거나, 후속 피드백 가능성이 없고 결과 통합까지 끝났을 때만 호출한다.
10. background 결과가 도착하면 메인 에이전트가 검토, 저장, 카드 반영, 최종 보고를 맡는다. 같은 일을 처음부터 다시 하지 않는다.

## Dispatch 절차

### 1. 분해

스폰 전 작업을 즉시 실행 단위와 백그라운드 단위로 나눈다.

- 즉시 실행 단위: 사용자와 지금 정해야 하는 판단, 카드 구조, 승인, 범위 정리.
- 백그라운드 단위: 장시간 조사, 독립 구현, QA, 리뷰, 보안 점검, 브라우저 검증.

즉시 다음 행동이 백그라운드 결과 없이는 불가능하면 foreground로 처리하거나, 스폰 후 `wait_agent`가 필요한 이유를 짧게 말한다.

### 2. 스폰

스폰 전 같은 역할/작업 라인의 기존 agent를 먼저 확인한다.

- 살아있는 agent가 있으면 `send_input`으로 후속 지시를 보낸다.
- 닫힌 agent라도 같은 맥락을 이어갈 가치가 있으면 `resume_agent` 후 `send_input`을 시도한다.
- 새 작업이 다른 파일 ownership, 다른 역할, 다른 위험 등급이면 새 agent를 만들 수 있다.
- 새 agent를 만들 때도 기존 agent와 write set이 겹치지 않게 분리한다.

subagent 프롬프트에는 아래를 반드시 넣는다.

- 미션 1줄
- 작업 범위와 금지 범위
- 수정 권한 여부
- 산출물 형식
- 시간 한도 또는 종료 기준
- 파일 소유권, 수정 가능 경로
- screenshot 생성 허용 여부와 저장 경로
- commit/push/PR 허용 여부

파일 쓰기 작업이면 "다른 작업자가 있을 수 있으니 타인의 변경을 되돌리지 말라"를 포함한다.

UI/browser-facing 작업이면 screenshot 생성 허용 여부와 저장 경로, 확인할 viewport, commit/push/PR 허용 여부를 명확히 적는다. 별도 mock 산출물은 기본 요구사항이 아니다.

### 3. 양보

스폰 직후 메인 응답은 짧게 끝낸다.

```text
백그라운드 디스패치 완료: {agent/nickname}에게 {작업}을 맡겼습니다.
저는 여기서 기다리지 않고, 지금은 {메인에서 계속할 작업/질문}으로 이어가겠습니다.
```

스폰 직후 같은 주제의 긴 foreground 조사를 계속하지 않는다. 필요한 경우에도 사용자 입력을 받을 수 있는 짧은 단위로만 진행한다.

### 4. 진행 중 사용자 입력 처리

사용자 입력을 아래처럼 해석한다.

- 상태 질문: 현재 알고 있는 agent 상태를 답하고 계속 둔다.
- 관련 구조 질문: 메인 에이전트가 답하되, background 작업은 유지한다.
- 새 작업 요청: 충돌하지 않으면 병행한다.
- 명시적 취소: 해당 agent를 닫고 취소 사실을 보고한다.
- 충돌 요청: 어느 작업을 우선할지 짧게 확인하거나, 충돌하지 않는 최소 조치만 한다.

## 금지

- `-bd` 요청 후 바로 `wait_agent`로 장시간 막기.
- 사용자가 새 질문을 했다는 이유만으로 background agent를 종료하기.
- 메인 에이전트가 background subagent와 같은 조사를 중복 수행하기.
- background 결과를 받기 전에 성공/완료로 보고하기.
- agent id를 잃어버렸는데 완료됐다고 추정하기.

## 완료 처리

background 작업이 끝나면 다음 순서로 통합한다. 결과 통합은 세션 종료와 다르다.

1. 결과를 읽고 요구 산출물이 있는지 확인한다.
2. 필요한 경우 파일 diff, 출처, 테스트 결과를 검증한다.
3. Vault/Todo/문서/코드에 반영할 항목만 반영한다.
4. 같은 역할/작업 라인의 후속 피드백이 예상되면 agent를 유지한다.
5. 작업 라인이 끝났거나 사용자가 종료를 지시했거나 세션 유지가 더 위험하면 `close_agent`로 닫는다.
6. 완료 보고에는 `디스패치한 것`, `통합한 것`, `검증한 것`, `남은 것`, `agent 유지/종료 상태`를 짧게 남긴다.

## 실패/중단 처리

- subagent가 실패하면 실패 이유와 unblock path를 보고한다.
- 사용자가 turn을 끊었거나 세션이 재개됐으면, 이전 background 작업을 취소로 추정하지 않는다.
- 현재 런타임에서 agent 상태를 확인할 수 없으면 "상태 확인 불가"라고 말하고, 임의로 완료/취소를 선언하지 않는다.
- agent가 많이 쌓였더라도 "정리" 지시 없이 임의 종료하지 않는다. 먼저 역할/작업 라인별로 유지할 agent와 종료 후보를 보고하고 확인한다.
