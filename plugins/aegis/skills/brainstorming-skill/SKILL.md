# Aegis 브레인스토밍 스킬

이 스킬은 Superpowers의 brainstorming 방법론과 구조화 브레인스토밍 절차를 Aegis에 맞게 합친 설계 관문이다. 구현 스킬이 아니라, 불명확한 아이디어를 승인 가능한 설계와 검증 가능한 결정으로 바꾸는 절차다.

## 사용 시점

다음 조건 중 하나라도 있으면 사용한다.

- 새 기능, 새 화면, 새 구성 요소, 동작 변경을 시작한다.
- 요구사항이 불명확하거나 성공 기준이 약하다.
- 접근 방식 2개 이상을 비교해야 한다.
- "브레인스토밍", "아이디어", "옵션 비교", "방향 결정", "어떻게 가는 게 좋아" 같은 요청이 있다.
- 다단계 전달 작업을 구현 전에 설계 단위로 나눠야 한다.

사용하지 않는 경우:

- 단순 설명, 의미 조회, 이미 명확한 버그 수정, 이미 승인된 작은 구현.
- 코드 리뷰, QA, 보안 점검처럼 별도 역할 스킬이 더 직접적인 작업.

## 하드 게이트

설계를 제시하고 사용자가 승인하기 전에는 구현, 초기 구조 생성, 운영 파일 수정, 구현용 하위 에이전트 배정을 하지 않는다.

단순 작업이면 절차를 짧게 압축할 수 있다. 그래도 목표, 성공 기준, 검증 방법은 명시한다.

## Discovery

유용한 아이디어를 생성할 만큼 문제 신호가 충분한지 먼저 확인한다.

입력값을 5차원으로 점검한다.

1. Actor: 문제를 겪는 구체적인 사람, 역할, 시스템이 있는가?
2. Current state: 지금 어떤 일이 벌어지고 있는가?
3. Success metric: 해결됐다고 볼 수 있는 결과가 있는가?
4. Tried or ruled out: 이미 시도했거나 제외한 접근이 있는가?
5. Primary constraint: 시간, 예산, 기술, 조직 같은 핵심 제약이 있는가?

규칙:

- 3개 이상 없으면 우선순위 높은 질문 최대 3개를 한 번에 묻고 답변 후 진행한다.
- 1-2개 없으면 가정을 명시하고 진행한다.
- 0개 없으면 즉시 진행한다.
- 질문 루프는 1회 이상 반복하지 않는다. 부분 답변도 수용하고 진행한다.

## Phase 1: 문제 프레이밍

해결책을 만들기 전에 문제를 재정의한다.

출력:

- 문제 진술: 현재 상태와 원하는 상태 사이의 간극을 능동태 1문장으로 쓴다.
- 숨겨진 가정 3개: "우리는 [X]라고 가정하고 있다" 형식으로 쓴다.
- 리프레임 3가지:
  - 사용자 목표 각도: 사용자가 궁극적으로 원하는 것
  - 시스템 제약 각도: 현재 시스템이 할 수 없는 것
  - 근본 필요 각도: 제시된 해결책을 걷어낸 더 깊은 필요

이 단계에서는 해결책 언어를 쓰지 않는다. "~할 수 있다", "옵션", "추천" 같은 표현은 Phase 2 이후로 미룬다.

## Phase 2: 발산 생성

가능한 해결책 공간을 넓힌다. 이 단계에서는 평가와 순위를 금지한다.

다음 6가지 기법을 모두 적용한다.

1. Direct: 가장 명백한 접근을 구체적으로 쓴다.
2. Inversion: 문제를 악화시키는 방법을 만든 뒤 반전한다.
3. Constraint Removal: 핵심 제약이 없다면 무엇을 만들지 쓴 뒤 현실 제약에서 근사치를 찾는다.
4. Constraint Addition: 시간, 코드량, 예산, 사용자 범위 중 하나를 10배 줄였을 때 살아남는 설계를 쓴다.
5. Analogy Import: 다른 도메인의 해결 메커니즘을 현재 문제로 번역한다.
6. Devil's Advocate: 생성된 주요 아이디어가 실제 환경에서 실패하는 구체적 이유를 명명한다.

출력 후 사용자가 고르지 않으면 가장 다양한 3-4개 아이디어를 Phase 3으로 가져간다.

## Phase 3: 관점 주입

선택된 아이디어를 점수화 전에 3개 렌즈로 검토한다. 아직 순위와 결론을 내리지 않는다.

- 회의론자: 핵심 가정, 확신도, 알려진 실패 전례, 1주일 안에 얻을 수 있는 반증 증거를 본다.
- 사용자/고객: 실제 사용자, 행동 변화량, 첫 반응, 동료에게 말할 가치 제안을 본다.
- 게으른 엔지니어: 20% 노력으로 80% 가치를 내는 최소 실행 가능 버전과 제거할 항목을 본다.

## Phase 4: 수렴과 순위화

각 아이디어를 4차원으로 1-5점 평가한다.

- 영향력: 목표에 의미 있는 변화를 만드는가?
- 노력: 낮은 구현 비용일수록 높은 점수다.
- 참신성: 쉽게 복제되지 않는 차별성이 있는가?
- 위험: 낮은 폭발 반경과 쉬운 롤백일수록 높은 점수다.

합계는 20점 만점이다. 2점 이내 동점이면 노력 점수가 높은 쪽을 먼저 고르고, 그래도 같으면 위험 점수가 높은 쪽을 고른다.

추천안은 점수만으로 정당화하지 않는다. Phase 3의 렌즈 발견을 최소 1개 이상 연결해서 설명한다.

## Phase 5: 결정 브리프

최종 출력은 사용자가 바로 승인하거나 수정할 수 있는 의사결정 브리프로 정리한다.

기본 형식:

```text
목표:
성공 기준:
문제 진술:
숨겨진 가정:
검토한 리프레임:
생성한 옵션:
평가:
추천 접근:
핵심 가정:
반증 기준:
검증:
승인 필요:
```

공식 설계 문서가 필요하면 프로젝트의 기존 설계 문서 위치에 저장한다. 위치가 없으면 아래를 사용한다.

```text
docs/aegis/specs/YYYY-MM-DD-topic-design.md
```

## 설계 원칙

- 각 단위는 목적, 인터페이스, 의존성 경계가 명확해야 한다.
- 기존 코드베이스 패턴을 먼저 따른다.
- 요청 목표에 직접 필요한 정리만 설계에 포함한다.
- 무관한 리팩터링을 묶지 않는다.
- 탈락한 옵션도 한 줄로 남긴다. 나중에 다시 쓸 수 있는 결정 근거다.

## 승인 후

사용자가 승인하면 `orchestration-harness-skill`로 돌아간다. 팀장이 작업 트리, 위임, 관문, 구현 계획을 정한다.
