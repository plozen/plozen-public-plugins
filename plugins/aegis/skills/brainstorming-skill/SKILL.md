# Aegis 브레인스토밍 스킬

이 스킬은 Superpowers의 brainstorming 방법론을 Aegis에 맞게 축약한 설계 관문이다. 구현 스킬이 아니라, 아이디어를 승인 가능한 설계로 바꾸는 절차다.

## 하드 게이트

설계를 제시하고 사용자가 승인하기 전에는 구현, 초기 구조 생성, 운영 파일 수정, 구현용 하위 에이전트 배정을 하지 않는다.

작은 변경도 예외가 아니다. 단순 작업이면 설계는 짧게 쓰되, 목표와 성공 기준은 명시한다.

## 절차

1. 프로젝트 맥락을 확인한다.
   - 관련 파일, 문서, 최근 커밋, 기존 산출물을 읽는다.
   - 요청이 작은 수정인지, 기능 추가인지, 여러 하위 시스템이 섞인 큰 프로젝트인지 분류한다.

2. 의도를 명확히 한다.
   - 질문은 한 번에 하나만 한다.
   - 사용자가 답하기 쉬우면 객관식으로 묻는다.
   - 목표, 제약, 대상 사용자, 성공 기준, 제외 범위를 확인한다.

3. 범위가 크면 쪼갠다.
   - 독립 하위 시스템이 여러 개면 먼저 하위 프로젝트로 나눈다.
   - 전체를 한 번에 구현하려 하지 말고 첫 하위 프로젝트부터 설계한다.

4. 접근안을 제시한다.
   - 가능한 접근안 2-3개를 제시한다.
   - 장단점과 추천안을 함께 말한다.
   - 지금 필요 없는 기능은 제거한다.

5. 설계를 제시한다.
   - 구조, 구성 요소, 데이터 흐름, 오류 처리, 검증 방법을 포함한다.
   - 위험이 작으면 짧게, 위험이 크면 섹션을 나눠 자세히 쓴다.
   - 구현 계획으로 넘어가기 전에 사용자 승인을 받는다.

6. 설계를 자체 점검한다.
   - 임시 문구, 애매한 요구사항, 내부 모순을 제거한다.
   - 성공 기준이 검증 가능한지 확인한다.
   - 구현 계획으로 나눌 수 있는 크기인지 확인한다.

7. 승인 후 오케스트레이션으로 넘긴다.
   - 승인되면 `orchestration-harness-skill`로 돌아간다.
   - 팀장이 작업 트리, 위임, 관문, 구현 계획을 정한다.

## 설계 원칙

- 각 단위는 목적, 인터페이스, 의존성 경계가 명확해야 한다.
- 기존 코드베이스 패턴을 먼저 따른다.
- 요청 목표에 직접 필요한 정리만 설계에 포함한다.
- 무관한 리팩터링을 묶지 않는다.

## 출력 형식

사용자가 공식 설계 문서를 요구하지 않으면 아래 형식을 쓴다.

```text
목표:
성공 기준:
추천 접근:
대안:
범위:
위험:
검증:
승인 필요:
```

공식 설계 문서가 필요하면 프로젝트의 기존 설계 문서 위치에 저장한다. 위치가 없으면 아래를 사용한다.

```text
docs/aegis/specs/YYYY-MM-DD-topic-design.md
```
